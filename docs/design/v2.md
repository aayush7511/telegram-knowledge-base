# v2 Design: Knowledge Graph

Decisions made before implementation. Frozen once committed — changes go in ROADMAP.md or CLAUDE.md, not here.

## What's done

As of v1: any Telegram message (text, URL, document) is durably stored in D1 and R2. Blog URLs are fetched, summarized via LLM, and replied to automatically. The pipeline is fully async — Worker 1 ACKs Telegram immediately, Worker 2 forwards to Cloud Run, Cloud Run handles processing. Nothing is retrievable after the fact; content is stored but not connected or searchable.

## What we're building

v2 connects the dots. Every item that passes through the pipeline — after summarization — gets written into a temporal knowledge graph (Graphiti + FalkorDB). The graph stores entities, relationships, and episodes with timestamps. When the user later asks a question in the chat, the bot searches the graph for relevant past content and grounds its response in what it already knows. The KB stops being a write-only archive and becomes something you can actually query through normal conversation.

## Curation policy

**Decision: store everything sent to the bot. Sending is the curation act.**

If you send it, it gets written to the graph. No clarifying questions, no ambiguity resolution at ingestion time. The user filters at the source — by choosing what to send to Telegram.

Rejected alternative: bot asks when intent is ambiguous (e.g. a 400-page PDF). Rejected because it adds friction to the happy path and the send-as-curation model is simpler and more consistent.

Non-goal: re-curation if this policy changes later. Already in ROADMAP.md v2 non-goals.

## Infrastructure

**FalkorDB on GCE e2-micro (always-free tier)**

- OS: Container-Optimized OS (COS) — ~150MB RAM footprint, Docker first-class
- FalkorDB Docker image: ~150MB RAM at runtime
- Disk: 30GB standard persistent HDD (always-free)
- Region: `us-central1`, `us-west1`, or `us-east1` (required for free tier)
- RAM budget: ~600MB headroom after OS + FalkorDB

**Cloud Run → FalkorDB connectivity**

- Static public IP on GCE VM (free when attached to a running instance)
- GCE firewall rule: allow port 6379 from Cloud Run IP ranges only (CIDR blocks, not a single IP — Cloud Run has no fixed outbound IP; Google publishes the ranges per region at their IP ranges JSON endpoint; look up ranges for whichever region the orchestrator runs in)
- FalkorDB password injected via environment variable (never hardcoded)
- VPC connector rejected: costs ~$5–15/month (minimum 2 underlying VM instances)

## Graph write pipeline

After the existing summarization step in the orchestrator, add a Graphiti write:

```
receive → verify → queue → forward → fetch → transcribe → summarize → [graph write] → saved
```

The graph write is synchronous within the Cloud Run request — it holds the request open. Graphiti extracts entities and relationships from the summary, writes episode + entity nodes + edges to FalkorDB.

If the graph write fails: log the error, mark job `failed`, do not silently skip. The summary is already in the Telegram reply so the user got value — the graph write failure is recoverable by re-processing from D1.

## Retrieval

When the user sends a message that looks like a question (LLM classifier, not keyword matching), the bot:

1. Runs Graphiti search against FalkorDB with the query text
2. Injects retrieved context into the LLM prompt
3. Generates a response grounded in past KB content

Non-question messages skip retrieval and go straight to ingestion.

## Global community recompute

Graphiti assigns new nodes to communities based on local neighborhood (greedy, incremental). This drifts over time as the graph grows. Fix: periodic full Leiden recompute via Python igraph.

**Schedule: weekly** (not daily — daily would exceed the 1GB/month GCE egress free tier if the graph grows large; weekly keeps egress well under the limit).

**Implementation: Cloud Run Job triggered by Cloud Scheduler**

- Cloud Scheduler fires weekly (free tier: 3 jobs)
- Cloud Run Job reads full graph from FalkorDB, runs Leiden via igraph, writes updated community labels back
- Separate from the main orchestrator service — its own lifecycle and timeout

Egress estimate at steady state (50MB graph, weekly): ~200MB/month. Well within the 1GB free tier.
