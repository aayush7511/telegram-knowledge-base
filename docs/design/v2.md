# v2 Design: Knowledge Graph (ingestion)

Decisions made before implementation. Frozen once committed — changes go in ROADMAP.md or CLAUDE.md, not here.

## What's done

As of v1: any Telegram message (text, URL, document) is durably stored in D1 and R2. Blog URLs are fetched, summarized via LLM, and replied to automatically. The pipeline is fully async — Worker 1 ACKs Telegram immediately, Worker 2 forwards to Cloud Run, Cloud Run handles processing. Nothing is retrievable after the fact; content is stored but not connected or searchable.

## What we're building

v2 makes the pipeline write into a temporal knowledge graph (Graphiti + FalkorDB) instead of replying and forgetting. Two kinds of job get written: blog URLs (the v1 summary becomes the graph episode) and plain-text notes (the note itself becomes the episode, no summarization). Each episode carries the time the message was received, and Graphiti extracts entities and relationships from it. Once everything from a message is in the graph, the bot's 👀 reaction on it changes to 👌. v2 is **ingestion only** — nothing reads the graph yet. Retrieval (questions in the chat, and a connector that Claude / Claude Code can query) and global community recompute are v3.

## Scope

| In v2 | Moved to v3 |
|---|---|
| Blog URL jobs → graph | In-chat questions answered from the graph |
| Plain-text notes → graph | Retrieval connector for Claude / Claude Code |
| `indexing` state + blog summary persisted in D1 | Weekly global Leiden community recompute |
| 👀 → 👌 reaction once a message's jobs are all `saved` | |
| FalkorDB VM + Direct VPC egress | |

Other content types (voice, photo, video, document, Instagram/YouTube URLs) keep today's stub behaviour.

## Curation policy

**Decision: store everything sent to the bot. Sending is the curation act.**

If you send it, it gets written to the graph. No clarifying questions, no ambiguity resolution at ingestion time. The user filters at the source — by choosing what to send to Telegram.

In v2 every plain-text message is treated as a note to store. Questions aren't sent to the bot until in-chat retrieval exists (v3), so there's no question/note classifier yet.

Rejected alternative: bot asks when intent is ambiguous (e.g. a 400-page PDF). Rejected because it adds friction to the happy path and the send-as-curation model is simpler and more consistent.

Non-goal: re-curation if this policy changes later. Already in ROADMAP.md v2 non-goals.

## Infrastructure

**FalkorDB on GCE e2-micro (always-free tier)**

- OS: Container-Optimized OS (COS) — ~150MB RAM footprint, Docker first-class
- FalkorDB Docker image: ~150MB RAM at runtime
- Disk: 30GB standard persistent HDD (always-free); FalkorDB's data directory lives on it so the graph survives VM restarts
- Region: `us-central1` (same region as the orchestrator; one of the three free-tier regions)
- RAM budget: ~600MB headroom after OS + FalkorDB
- FalkorDB password injected via environment variable (never hardcoded)

**Cloud Run → FalkorDB connectivity: Direct VPC egress**

- Cloud Run joins the VPC directly (`--network default --subnet default --vpc-egress private-ranges-only`) and reaches FalkorDB on the VM's internal IP.
- `private-ranges-only` is load-bearing: only traffic to private (RFC 1918) addresses goes through the VPC. Gemini, Telegram, and blog fetches keep going straight to the internet. `all-traffic` would need Cloud NAT to reach the internet, which is paid.
- Firewall: allow tcp:6379 only from the subnet Cloud Run uses, only to the FalkorDB VM's network tag. Port 6379 is never open to the internet.
- The VM keeps its external IP for outbound traffic (image pulls, OS updates) — free on the free-tier e2-micro.
- Cost: no compute charge — unlike a Serverless VPC Access connector, which runs ≥2 VMs at ~$5–15/month. Only per-GB network transfer: free within a zone, ~$0.01/GB between zones in the same region. Cloud Run can't be pinned to a zone, so expect fractions of a cent per month — accepted as effectively $0.
- Rejected: public IP + firewall on Cloud Run's published IP ranges. Those ranges are shared by every GCP customer in the region, so the firewall barely narrows access, and the Redis protocol would carry the password in plaintext over the internet.

## Graph write pipeline

Blog URL jobs:

```
forwarded → fetching → summarizing → [Telegram reply] → indexing → [graph write] → saved
```

Text notes:

```
forwarded → indexing → [graph write] → saved
```

- **`indexing` state** — new, between `summarizing` and `saved`. Passes the state-machine litmus test: "died while writing to the graph" is a distinct, actionable failure. Worker 2 adds it to `REPORTABLE_STATES`, and `applyStatusUpdate` gains transition validation (it currently writes any reportable state unguarded).
- **Episode body** — blog: title + summary only; URL, site, and author go in `source_description` (`blog: <url> | site: <site> | author: <author>`). Graphiti's text-extraction prompt never sees `source_description`, so metadata stays provenance on the Episodic node instead of becoming entities — in M0 a metadata header turned `anthropic.com`, `paulgraham.com`, and "GitHub" (from a URL) into entities and crowded out real content. Trade-offs: authors and the publishing organization become entities only if the summary names them, and an abstract post that names nothing can yield no entities (the episode itself is still stored). On rebuild from D1, `source_description` is recomputed from the `url` column; site and author are provenance only and aren't persisted. Text note: the message text as sent.
- **Blog summary persisted in D1** — new `summary TEXT` column (migration `0003`), written by the `indexing` status post. It stores the exact blog episode body, so the graph can be rebuilt by replaying D1 without re-fetching pages that may have changed. Text notes don't need it — their content is already in the `text` column. ~1–2KB per job, negligible against D1's 5GB free tier. Status posts are best-effort, so a lost post leaves one row without a summary; the graph write still proceeds.
- **Episode metadata** — `reference_time` = the job's `time_received`. Episodes are keyed by `job_id` so re-processing a job doesn't duplicate it. `add_episode(uuid=...)` only *reprocesses* an existing episode (it raises `NodeNotFoundError` otherwise), so `write_episode` first upserts the Episodic node with `uuid = job_id` (its save is a MERGE), then calls `add_episode(uuid=job_id)`. One fixed Graphiti `group_id` for the whole graph — unrelated to the job descriptor's `group_id` (album / URL fan-out id). On FalkorDB the `group_id` *is* the graph name: set the driver's `database` to the same value, or every `add_episode` clones the driver onto a different graph (and each clone starts its own background index build).
- **Synchronous** — the graph write holds the Cloud Run request open, like the rest of the pipeline. Graphiti makes several LLM calls per episode, so a job can take minutes under free-tier rate limits: raise Cloud Run `--timeout` and set Worker 2 `max_batch_size` to 1 (currently 5) so a serially-processed batch can't outlive the queue consumer's wall-clock limit.
- **Failure** — log, mark `failed` with the error, never silently skip. For blog jobs the user already has the summary reply; the graph entry is recoverable from D1.

## Reactions: 👀 → 👌

- **👀 (unchanged)** — Worker 1 already reacts 👀 on every message it accepts, right after enqueueing, text notes included.
- **👌 when everything from the message is saved** — when Worker 2 applies a `saved` status update, it checks D1 for every job from the same Telegram message (`chat_id`, `message_id`). If all are `saved`, it calls `setMessageReaction` with 👌, which replaces the 👀 (bots get one reaction per message).
- **Why Worker 2, not Cloud Run** — Worker 2 owns D1 and sees every `saved` transition, so the all-jobs check is one query. A multi-link message fans out into several jobs sharing one message; only the last one to finish knows the message is complete.
- **Best-effort** — the reaction runs via `ctx.waitUntil`; a failure is logged and never fails the status update. Worker 2 needs `TELEGRAM_BOT_TOKEN` as a Wrangler secret (the Telegram call is duplicated from Worker 1, per the self-contained-workers rule).
- **Races are harmless** — each check runs after its own write, so the last sibling to save always sees the complete set. Two siblings saving at once can both react; the call is idempotent.
- **Stays 👀** — a message with any `failed` job (a failure reply is v4), and a message mixing a blog link with an Instagram/YouTube link until v3 processes the latter.
- **Not ✅** — it isn't in Telegram's allowed bot-reaction set; the API rejects it with `REACTION_INVALID`.
- **No reply for text notes** — the reaction is the acknowledgement. A clear final reply for every item is a v4 goal.

## Graphiti LLM provider

Graphiti needs an LLM (entity/edge extraction and dedup) and an embedder. Its LLM config has two slots — `model` for the main prompts and `small_model` for ones it treats as simpler. An unset `small_model` silently falls back to `gpt-4.1-nano`, so both are set explicitly.

**Decision: OpenAI `gpt-4.1-mini` in both slots, on OpenAI's data-sharing complimentary tokens — confirmed in M0 over `gpt-5-nano` (see [M0 results](#m0-results-2026-09-11)).**

- **Why OpenAI** — Graphiti's default provider, with the most reliable structured output; the Zep paper built its benchmark graphs with `gpt-4o-mini`. `gpt-4.1-mini` over `gpt-4o-mini`: newer and stronger at structured extraction, and within the free tokens the price difference doesn't matter.
- **Why one model in both slots** — mini and nano draw from the same free token pool, so nano saves nothing; very small models frequently emit JSON that doesn't match Graphiti's schemas (per Graphiti's own docs); one model is simpler to evaluate and pin.
- **Why test `gpt-5-nano`** — newer model family, and the cheapest option if the free program ever ends. It's a reasoning model: reasoning tokens bill as output and add latency, so M0 checks whether it holds up on Graphiti's schemas and how long an episode takes.
- **Cost** — $0 within 2.5M tokens/day across mini/nano models (usage tiers 1–2), roughly 70 episodes/day at the current per-episode estimate. Requires a one-time $5 prepaid credit to reach tier 1, opting in to OpenAI training on this project's API traffic, and auto-recharge off so overage can only draw down that credit. If the program ends: ~$0.02/episode on `gpt-4.1-mini` at list price (estimate).
- **Pinning** — the dated snapshot (e.g. `gpt-4.1-mini-2025-04-14`), not the alias, confirmed with a real request in M0.
- **Temperature 0** — Graphiti defaults to 1, which makes extraction vary from run to run; 0 makes reprocessing a job reproduce the same extraction (decided after M0's temperature check).
- **Embeddings** — OpenAI `text-embedding-3-small`. Gemini's free embeddings were tried in M0 and rejected: the free tier allows 100 embedding requests/minute and Graphiti's Gemini embedder sends one request per item, so the quota ran out by the fourth episode. OpenAI's embedder batches the whole list into one request. Probably not covered by the complimentary tokens, so it draws from the prepaid credit — $0.02 per 1M tokens, fractions of a cent per month. Effectively permanent once data is written — changing it means re-embedding the whole graph.
- **Fallback** — Gemini Flash-Lite on the free tier if the OpenAI program ends. Not the primary because Google revises free limits without notice.

**Groq is excluded.** It's reserved for ASR (v3) and future text tasks — Graphiti's per-episode call volume would burn that free tier (8K tokens/min, 200K tokens/day on the chat models). Groq's structured-output mode also has reported problems Graphiti would hit: optional schema fields unsupported, and non-JSON responses when there's nothing to extract.

## Implementation milestones

1. **M0 — Spike (no production code).** The same set of real blog summaries and sample text notes through Graphiti against a local FalkorDB container, once with `gpt-4.1-mini` and once with `gpt-5-nano` (same model in both slots, a separate graph per run). → verify: tokens, wall time, and schema failures per episode recorded; extracted entities/edges read side by side; model confirmed or switched; snapshot, `graphiti-core`, and embedding versions pinned; episode-keying approach confirmed.
2. **M1 — Infrastructure.** e2-micro + COS + FalkorDB (password, persistent data dir); Direct VPC egress on Cloud Run; firewall; raised `--timeout`; Worker 2 `max_batch_size` 1; $0.01 budget alert. → verify: Cloud Run gets `PONG` from the VM's internal IP, 6379 on the external IP is refused, graph data survives a VM restart.
3. **M2 — Worker 2: `indexing`, summary column, 👌 reaction.** Migration `0003`; Worker 2 accepts `indexing` and an optional `summary`; transition validation in `applyStatusUpdate`; all-jobs-saved check + 👌 reaction (new `TELEGRAM_BOT_TOKEN` secret). → verify: `workers/forward` vitest (Telegram stubbed the way `workers/ingest/vitest.config.ts` does) covers `indexing` accepted, summary stored, a missing summary doesn't overwrite an existing one, invalid transitions rejected, 👌 sent only when the last job of a multi-job message saves, a failed reaction still returns 200. Deploy together with M3 — v1 blog jobs already reach `saved`, so shipping M2 alone would put 👌 on items that never reached the graph.
4. **M3 — Graph writes (orchestrator).** `graph.py` (lazy Graphiti + `FalkorDriver` — the driver connects to FalkorDB in its constructor, so it must never be built at import time, and when built inside a running event loop it starts its own index build as a background task: await that task before the first write rather than calling `build_indices_and_constraints()` again, which races it; `write_episode`); blog pipeline gains `indexing` → graph write → `saved`; text jobs get their own `indexing` → graph write → `saved` path. Silence any logger that prints connection details. → verify: offline pytest for step ordering and failure → `failed` (reply still sent for blogs); then a real run of a blog URL and a text note, each reaching `saved` in D1 with its episode in FalkorDB and 👌 on the message.
5. **M4 — Docs.** CLAUDE.md, README, orchestrator and forward READMEs (new env vars/secrets, deploy flags), architecture diagram.

## Moved to v3

Kept here so the v3 design can pick them up.

**Retrieval.** Two paths: (1) in-chat — when a message looks like a question (LLM classifier, not keyword matching), run Graphiti search against FalkorDB, inject the results into the prompt, and reply with a grounded answer; (2) a separate connector that lets Claude / Claude Code query the graph directly. Deferred until there's more LLM budget.

**Global community recompute.** Graphiti assigns new nodes to communities based on local neighborhood (greedy, incremental), which drifts as the graph grows. Fix: periodic full Leiden recompute via Python igraph.

- Schedule: weekly — daily could exceed the 1GB/month GCE egress free tier as the graph grows. Steady-state estimate (50MB graph, weekly): ~200MB/month.
- Implementation: Cloud Run Job triggered by Cloud Scheduler (free tier: 3 jobs); reads the full graph from FalkorDB, runs Leiden, writes community labels back. Separate from the orchestrator — its own lifecycle and timeout.
- To revisit: whether weekly is frequent enough at 10k+ nodes; whether to expose clusters via a bot command (e.g. `/topics`).

## M0 results (2026-09-11)

Harness: [spikes/m0-graphiti/](../../spikes/m0-graphiti/). 8 real blog posts — three overlapping on agent memory / knowledge graphs, two on LLM agents, an LLM-landscape review, Cloudflare Queues, and an unrelated Paul Graham essay as a control — summarized once with the orchestrator's prompt, then ingested into a fresh FalkorDB graph per model. Text notes weren't included.

| | `gpt-4.1-mini-2025-04-14` | `gpt-5-nano-2025-08-07` |
|---|---|---|
| Episodes ingested | 8/8 | 8/8 |
| Avg time per episode | 13.0s | 10.3s |
| Avg tokens per episode (in / out) | 11.2K / 0.6K | 10.1K / 0.6K |
| LLM calls per episode | 6.9 | 6.4 |
| Schema retries / errors | 0 / 0 | 0 / 0 |
| Unique entities / facts in the graph | 42 / 30 | 28 / 23 |
| Entities shared across episodes | 2, both correct (Zep, large language models) | 10, mostly false |
| Re-add under the same uuid → new entities / facts | 0 / 0 | 0 / 2 |

**`gpt-4.1-mini` confirmed.** `gpt-5-nano` was faster but linked entities to episodes that never mention them: the Lilian Weng agents episode was linked to Daniel Chalef, Brenda Potts, MemGPT, PyPI, Redis Graph, and FalkorDB (all from earlier episodes), and the Paul Graham control to GitHub. False links are the worst failure for a knowledge graph — retrieval would surface them as real connections. It also split "Zep" from "Zep - Agent memory at enterprise scale", dropped the GraphRAG entity from its own episode, and added 2 facts when an episode was re-added. Its speed and price advantages don't matter inside the free tokens.

**Free-token headroom:** ~11.8K tokens per episode (it grows as the graph grows, since dedup prompts carry existing entities), so the 2.5M/day complimentary pool covers roughly 200 episodes/day.

**Pinned:** `graphiti-core==0.30.2`; `gpt-4.1-mini-2025-04-14` in both slots; `text-embedding-3-small` (truncated to Graphiti's default 1024 dimensions); FalkorDB image `falkordb/falkordb@sha256:adbddd418916c25618564ff8597a919b08bc76452ebeb74eb985c38d7281df62` (graph module version 42004).

**Findings already folded into the sections above:**
- Keying by `job_id` = upsert the Episodic node, then `add_episode(uuid=job_id)`. Re-adding an episode created no new entities or facts on `gpt-4.1-mini`.
- On FalkorDB, `group_id` must equal the driver's `database`.
- `FalkorDriver` starts its own background index build; a second `build_indices_and_constraints()` races it.
- Gemini's free embeddings ran out after 3 episodes (100 requests/min, one request per item) → OpenAI embeddings.
- `gemini-3.6-flash` returned transient 503s during the spike; the orchestrator's summarizer only retries 429s (filed as a separate task).

**Extraction quality (`gpt-4.1-mini`):** strong on entity-dense posts — Lilian Weng's agents post gave 14 real concepts (Chain of Thought, Tree of Thoughts, ReAct, Reflexion, HNSW, FAISS, HuggingGPT…), and GraphRAG and the Graphiti/FalkorDB post came out clean. Thin on abstract posts: Anthropic's "Building Effective AI Agents" and the Paul Graham essay produced only the site and the title, and "Anthropic" was never extracted. Part of that noise comes from the metadata header in the episode body — site and URL became entities (`anthropic.com`, `paulgraham.com`, "Cloudflare Blog", "Lil'Log", and GitHub from the `lilianweng.github.io` URL).

**Episode format re-run (`gpt-4.1-mini`, same summaries):** URL, site, and author moved from a header in the episode text into `source_description`, which Graphiti's text-extraction prompt never sees.

|---|---|---|
| Metadata-looking entities | 5 (`Lil'Log`, `GitHub`, `anthropic.com`, "Cloudflare Blog", `paulgraham.com`) | 0 |
| Unique entities / facts | 42 / 30 | 39 / 35 |

Adopted — see *Episode body* above. Costs: the authors (Lilian Weng, Daniel Chalef) and the Zep → Graphiti link came only from the header and are gone, and "Anthropic" isn't extracted because its own summary never names it. This run also made one false link — HuggingGPT attached to Simon Willison's 2024 review, whose summary never mentions it — and dropped the Apple MLX entities the baseline run found.

**Temperature check:** Graphiti defaults to temperature 1, so extraction varies from run to run, and every comparison above is a single run. A minimal check re-ran just the pair behind the format re-run's false link (Lilian Weng's post, then Simon Willison's review) at temperature 0 and at 1 (~25K tokens): neither reproduced the HuggingGPT link, and both recovered the Apple MLX entity — so that link came from the larger 8-episode graph and/or chance, not temperature alone. Temperature 0 is pinned anyway (see *Graphiti LLM provider*).
