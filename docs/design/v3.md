# v3 Design: Reach, retrieval + public brain

Decisions made before implementation. Frozen once committed — changes go in ROADMAP.md or CLAUDE.md, not here.

**Status: draft (2026-09-26).** Scope is set in [ROADMAP.md](../../ROADMAP.md#v3--reach-retrieval--public-brain). Decisions so far: [Decisions](#decisions), [Link filtering](#link-filtering), and the resolved open questions; the rest are open.

## What's done

As of v2: any Telegram message (text, URL, document) is durably stored in D1 and R2. Blog URLs are rendered, extracted, summarized, and replied to. Blog articles (full cleaned text) and plain-text notes are written into a temporal knowledge graph: Graphiti on Cloud Run, backed by FalkorDB on a GCE e2-micro reached over Direct VPC egress. Extraction uses `gpt-4.1-mini` at temperature 0 and embeddings use `text-embedding-3-small`. The bot's 👀 changes to 👌 once everything from a message is in the graph. Everything lives in one graph, `second-brain`. Nothing reads the graph yet. Instagram/YouTube URLs and native media are accepted and stored, but not processed.

## What we're building

v3 does three things, all within the $0 constraint. It widens what the bot can read: links to YouTube, X, Reddit, Stack Overflow, and GitHub get fetched and processed like blog URLs, using the text each source already has (captions, post text, answers). PDFs are supported too, both as links and as files sent in Telegram. Links to pages with nothing to remember (profiles, search pages, empty or blocked pages) get a "not supported" reply instead of being saved. It makes the graph usable from other tools: questions asked in the Telegram chat get grounded answers, and an MCP connector lets Claude Code, Codex, and other MCP clients both query the graph and save to it. And it puts a **public brain** online: a read-only page where anyone can browse the graph of what the owner reads and ask it questions. That last part forces a hard split between public and private content, and a cap on what public queries can cost. Audio transcription (native media, captionless videos, Instagram reels) is v4.

## Decisions

- **Agent-Reach is a reference, not a dependency.** [Agent-Reach](https://github.com/Panniantong/Agent-Reach) (MIT) is a router for interactive coding agents. It installs and health-checks other people's tools, and it switches between them automatically when a platform breaks one ("Bilibili 412-blocked yt-dlp → switched to bili-cli, zero action on your side"). That conflicts with our pinning rule, and its tools are built to search and browse, while we need to fetch the one item behind a URL. We use its research to pick one pinned tool per source (below). The owner can still install it as a Claude Code skill; that's independent of this project.
- **"Search anything" means ingesting any link sent to the bot.** The bot doesn't search the web. Claude Code and Codex already do that themselves; this project's job is to remember.
- **The MCP connector is read + write.** Mid-conversation, Claude can save something to the graph ("remember this link"), not just query it.
- **Links inside a fetched post become their own jobs.** A post like "Nice @nytimes article… <url>" is saved as-is, and each URL in it is processed separately, as if it had been sent on its own. This applies to X now, and the same rule fits Reddit link posts. Proposed mechanics, to confirm when building:
  - **Only Worker 1 creates jobs.** Cloud Run finds links only after fetching, so it asks Worker 1 to create the children through a new internal endpoint behind `X-KB-Secret`. That reuses Worker 1's Layer-1 URL checks and writes each D1 row before enqueueing, so every job stays rebuildable from D1. The MCP save path can use the same endpoint.
  - **Children carry the parent's `chat_id` / `message_id`,** so `allJobsSaved` holds the 👌 until they're done too. D1 already allows several rows per message (multi-URL fan-out). Children must be created before the parent reaches `saved`, or 👌 fires early; creating them during `fetching` guarantees that.
  - **One level deep.** A child's own links aren't fanned out again, which stops chains and loops. That needs a `parent_job_id` column (migration `0004`), which also records where the link came from.
  - **Which links:** the post's expanded URLs (FxTwitter already resolves `t.co`). A quoted post's text goes into the parent's episode instead of becoming a child job.

Two notes that outlive v3:
- **OpenCLI** (Apache-2.0, ~30k★) turns any website into a command-line tool by driving a real logged-in Chrome. It can't run headless, but on the Pi with a desktop session it's the catch-all for sites that need a login — Instagram's likely path in v4.
- **RSS** is a feed a site publishes listing its new posts; subscribing pulls each new post in automatically. It's a different mode from sending a link: the bot would ingest everything a subscribed site publishes, which breaks the curation policy ("sending is the curation act") and needs a scheduled job. Parked in ROADMAP future ideas.

## Link filtering

**Decision: a link to something with nothing to remember gets a "not supported" reply and is never saved.** Two checks, matching the existing two-layer URL validation:

1. **Before fetching (Worker 1, by URL shape).** Profiles, feeds, listings, search pages, and anything else that's navigation rather than content are rejected with the existing "Skipped (not ingestible): <url> — <reason>" reply. No job is created.
2. **After fetching (Cloud Run, by content).** If the page turns out to have no useful content, it isn't summarized or written to the graph. The bot replies "not supported: <reason>" and the job ends `failed` with that reason. See [No useful content](#no-useful-content).

Playwright stays as the blog renderer. Only the "save whatever came back" behavior goes.

For the first check, the rules live in one table in `workers/ingest/src/urls.ts` (host + path pattern + reason), so adding a rule later is one line. This is the same Layer-1 check that already rejects Instagram profiles and YouTube channels; it now covers the new sources and adds a set of general rules for any host.

Today any unrecognized link is treated as a blog, so an X profile or a Google search page currently goes into the blog pipeline, gets rendered, and saves whatever the page shows (often a login wall).

**Accepted**, by source:

| Source | Accepted | Notes |
|---|---|---|
| X (`x.com`, `twitter.com`, `mobile.twitter.com`) | `/{user}/status/{id}`, `/i/status/{id}`, `/i/web/status/{id}` | Suffixes like `/photo/1` and `/analytics` are dropped. Articles are fetched through their post's status URL |
| Reddit (`reddit.com`, `www.` / `old.` / `new.` / `np.` / `m.`, `redd.it`) | `/r/{sub}/comments/{id}/…` (post), `/r/{sub}/comments/{id}/{slug}/{comment_id}` (that comment), `/comments/{id}`, `redd.it/{id}`, `/r/{sub}/s/{token}` share links (resolved when fetched) | **Post only, no comments.** A comment link saves that comment, with the post's title for context |
| Stack Exchange (`stackoverflow.com`, `*.stackexchange.com`, `superuser.com`, `serverfault.com`, `askubuntu.com`, `mathoverflow.net`) | `/questions/{id}/…`, `/q/{id}`, `/a/{id}` | |
| GitHub (`github.com`, `gist.github.com`) | Repo root `/{owner}/{repo}`, `/issues/{n}`, `/pull/{n}`, a gist | Discussions are rejected for now ("GitHub discussions aren't supported yet"): no REST endpoint, and the rendered page carries every comment |
| YouTube | Unchanged from v1 | |
| PDF (any host) | Paths ending `.pdf` | A PDF without the extension (e.g. `arxiv.org/pdf/{id}`) is caught at fetch time by its `application/pdf` Content-Type and routed to PDF extraction. PDF files sent in Telegram arrive as `document` jobs, already stored in R2 |

**Rejected**, by source:

| Source | Rejected | Reason shown |
|---|---|---|
| X | Profiles `/{user}` and their tabs (`/with_replies`, `/media`, `/likes`, `/followers`, `/following`), `/search`, `/explore`, `/home`, `/hashtag/…`, `/i/lists/…`, `/i/communities/…`, `/messages`, `/notifications`, `/settings` | "X profile/page, not a post" |
| X | `/i/spaces/…` | "X Spaces are audio — not until v4" |
| Reddit | Subreddits `/r/{sub}` and their sorts (`/hot`, `/new`, `/top`…), `/r/popular`, `/r/all`, users `/user/…` / `/u/…`, multireddits, `/search`, the home page | "Reddit subreddit/user/listing, not a post" |
| Reddit | `i.redd.it`, `v.redd.it` | "Reddit-hosted image/video — not until v4" |
| Stack Exchange | `/questions` (lists), `/questions/tagged/…`, `/tags`, `/users/…`, `/search`, the home page | "Stack Exchange listing/profile, not a question" |
| GitHub | Users and orgs `/{owner}`, `/search`, `/topics`, `/trending`, `/explore`, `/marketplace`, `/settings`, `/notifications`; repo listings (`/issues`, `/pulls`, `/commits`, `/branches`, `/actions`, `/stargazers`, `/network`, `/tree/…`) | "GitHub profile/listing, not a repo, issue, or PR" |

**Rejected, any host:**

| Kind | Examples | Reason shown |
|---|---|---|
| Search results | `google.*/search`, `bing.com/search`, `duckduckgo.com/?q=`, `search.yahoo.com` | "search results page" |
| Maps | `google.*/maps`, `maps.app.goo.gl`, `maps.apple.com` | "map link" |
| Invites and meetings | `zoom.us/j/…`, `meet.google.com`, `teams.microsoft.com`, `discord.gg`, `discord.com/invite`, `t.me`, `chat.whatsapp.com`, `wa.me`, `calendly.com` | "invite/meeting link" |

| Behind a login | `docs.google.com`, `drive.google.com`, `dropbox.com` | "needs a login — can't fetch" |
| Hacker News listings | `news.ycombinator.com` except `/item?id=…` | "Hacker News listing, not a post" |
| Platforms not supported yet | `tiktok.com`, `facebook.com`, `linkedin.com`, `threads.net` / `threads.com` | "not supported yet" (they render as login walls today) |
| Files | Links ending `.zip`, `.exe`, `.dmg`, `.pkg`, `.msi`, `.apk`, `.iso`, `.tar.gz` | "file download, not a page" |
| Images, audio, video files | `.png`, `.jpg`, `.gif`, `.webp`, `.svg`, `.mp3`, `.mp4`, `.mov`, `.wav` | "media file — not until v4" |
| Private network | `localhost`, `127.*`, `10.*`, `172.16–31.*`, `192.168.*`, `169.254.*`, `*.local`, `*.internal`, IPv6 loopback / link-local | "private network address" |

**Until each source's fetcher is built,** links Worker 1 now labels `x`, `reddit`, `stackexchange`, `github`, or `pdf` go to the orchestrator's placeholder, the same way YouTube and Instagram links do today: they sit at 👀. Before, they went through the blog pipeline and saved whatever the page rendered.

**The private-network rule is a security fix, not tidiness.** Cloud Run can reach private IPs through Direct VPC egress, including FalkorDB (`10.128.0.2`) and its browser UI (port 3000). Once links inside fetched posts become their own jobs (see Decisions), link targets can come from a stranger's post, not just the owner. Layer 1 catches literal addresses, including disguised forms (`http://2130706433/` parses to `127.0.0.1`). At fetch time (`fetcher.render`, built 2026-09-26), Cloud Run resolves every request the browser routes (the first navigation and every subresource) and aborts any that points at a non-public address. Redirect hops bypass Playwright's routing (verified: neither `page.route` nor fulfilling the 3xx sees the next hop), so every request is also recorded, and if any reached a non-public address the page is discarded before extraction. A redirect can still cause one blind GET, but nothing it returns is kept, and the internal targets are safe from a bare GET: Redis drops HTTP, and the GCP metadata server requires a header browsers can't send. Live check: a public page redirecting to `127.0.0.1`, a public hostname resolving to it (`localtest.me`), and a literal address all got "not supported"; ordinary articles and public-to-public redirects still saved. Resolve-then-connect leaves a DNS-rebinding window between the check and Chromium's own lookup; the recorded-requests check narrows it but doesn't close it.

### No useful content

What counts as "no useful content", measured on real pages (plain download + Trafilatura, 2026-09-26):

| Page | Extracted text |
|---|---|
| The 8 M0 blog posts, Substack, Hugging Face, react.dev | 6K–67K chars |
| Hacker News front page | 4K chars |
| GitHub home page | 2K chars |
| Medium, OpenAI, NYT | Blocked by bot protection (403): 41–460 chars of error page |

- **HTTP error** (4xx/5xx after redirects): "not supported: the site returned HTTP <status>".
- **Too little text**: under `MIN_ARTICLE_CHARS` = 1,000 extracted chars (tune on real traffic), "not supported: no article text found". That catches login walls, bot-challenge pages that answer 200, and empty shells. It doesn't catch busy listing pages; those are what the URL rules are for.

Built 2026-09-26 (`fetcher.PageBlocked`, `main.MIN_ARTICLE_CHARS`). Checked with the real Playwright renderer:

| Page | Outcome |
|---|---|
| Lilian Weng, Anthropic, Paul Graham | Saved (38K, 13K, 67K chars) |
| Medium, NYT | Not supported: HTTP 403. Playwright doesn't get past their bot protection either |
| OpenAI | Not supported: no article text (a 200 challenge page, 100 chars) |
| example.com | Not supported: no article text (112 chars) |
| A 404 | Not supported: HTTP 404 |
| Hacker News front page | Saved (4.5K chars), so it got a URL rule: listings rejected, `item?id=` pages kept |
- **Page metadata can't be the test.** Only 6 of the 10 real articles above declare themselves as an article in structured data; Anthropic, Simon Willison, and Paul Graham don't.

**Later:** short links (`bit.ly`, `t.co`, `tinyurl.com`) are accepted and resolved when fetched, so the URL rules never see their real destination. Resolving them in Worker 1 first is parked in ROADMAP future ideas; the fetch-time checks still apply.

## Open questions

### Reach

1. ~~**Does the Pi happen in v3?**~~ **Resolved by [spike](../../spikes/youtube-transcript/): no.** From a GCP IP with no proxy, 6/6 caption fetches succeeded, but they took 4–154s against ~1s from home. YouTube runs on Cloud Run with a per-fetch timeout; blocks and timeouts end as `failed`. Fallbacks if production gets blocked: Webshare's free static proxies, then the Pi.
2. ~~**X long-form.**~~ **Resolved by [spike](../../spikes/x-fxtwitter/): FxTwitter alone.** Long posts, threads (from any post in them, author only), and Articles all come back whole. Articles arrive as Draft.js blocks that we flatten ourselves. Untested: threads longer than 3 posts.
3. ~~**URL validation for new sources.**~~ **Decided — see [Link filtering](#link-filtering).**
4. ~~**Episode shape per source.**~~ **Decided:** an X post is saved with the author's own thread (all of their posts in it, in order, fetched from any post in the thread via FxTwitter's `/2/thread`), and no one else's replies; a Stack Overflow question with its accepted answer; a GitHub repo as its README only; a Reddit post as just the post, and a link to a comment as that comment with the post's title for context. A Stack Overflow question with no accepted answer gets its top-voted answer, and a question with no answers is saved alone. A GitHub issue or PR is its title and description, no comments.

### Partition (resolve before any retrieval code)

5. **Two graphs or one?** Filtering one graph when it's read isn't safe: Graphiti merges an entity across every episode that mentions it, so a public entity's summary and facts can carry details from a private note. The candidate is two Graphiti graphs (on FalkorDB, `group_id` = graph name), with owner retrieval querying both. Cost: a private note no longer links to entities from public articles.
6. **Which side does each content type default to** (blog/YouTube public; notes and voice private?), and how does a message override it? This extends the curation policy ("sending is the curation act") with a visibility decision.
7. **Rebuilding the existing graph.** `second-brain` holds both kinds of content today. Rebuild it into the split from D1 (every row carries enough to replay), then retire it.

### Retrieval

8. **In-chat questions vs. notes.** v2 treats every plain-text message as a note. v3 needs a classifier (the v2 design says an LLM, not keywords) or an explicit command (`/ask`). A misclassified note is lost content, and a misclassified question pollutes the graph.
9. **MCP server: Graphiti's own or ours, and hosted where?** Cloud Run behind a bearer secret is the obvious candidate, since FalkorDB is VPC-private. Read + write is decided. Proposal for writes: an MCP save goes through the same ingest path as a Telegram message (a D1 job row, then the queue) rather than straight into Graphiti, so every graph entry stays rebuildable from D1. Open: which side (public/private) an MCP save defaults to.

### Public brain

10. **What a public answer may contain.** Blog episodes hold the full article text, so episode content must never reach a visitor. Public answers come from facts, entities, and `source_description` links only.
11. **Query cost and abuse.** What's the daily cap, enforced in the Worker before anything reaches Cloud Run? What do visitors see once it's hit? Are answers LLM-written, or just the returned facts (cheaper, and nothing for a prompt injection to steer)?
12. **Where the page lives.** Candidate: a Cloudflare Worker/Pages front end → a Cloud Run query endpoint behind `X-KB-Secret`. FalkorDB stays VPC-private, and its browser UI (port 3000) stays tunnel-only.

### Scope

13. **Does Leiden stay in v3?** v3 is now the largest version, and community recompute improves retrieval but isn't needed for any v3 user journey.
