## What's done

As of v2: any Telegram message (text, URL, document) is durably stored in D1 and R2. Blog URLs are rendered, extracted, summarized, and replied to. Blog articles (full cleaned text) and plain-text notes are written into a temporal knowledge graph: Graphiti on Cloud Run, backed by FalkorDB on a GCE e2-micro reached over Direct VPC egress. Extraction uses `gpt-4.1-mini` at temperature 0 and embeddings use `text-embedding-3-small`. The bot's 👀 changes to 👌 once everything from a message is in the graph. Everything lives in one graph, `second-brain`. Nothing reads the graph yet. Instagram/YouTube URLs and native media are accepted and stored, but not processed.

## What we're building

v3 does two things, both within the $0 constraint. It widens what the bot can read: links to YouTube, X, Stack Overflow, GitHub, and Instagram get fetched and processed like blog URLs, using the text each source already has (captions, post text, answers). PDFs are supported too, both as links and as files sent in Telegram. Links to pages with nothing to remember (profiles, search pages, empty or blocked pages) get a "not supported" reply instead of being saved. And it makes the graph usable from other tools: an MCP connector lets Claude Code, Codex, claude.ai, and other MCP clients both query the graph and save to it. It also transcribes audio (voice memos and videos sent to the bot, YouTube videos with no captions, Instagram reel audio) with Groq's free Whisper tier. And it opens up to the owner plus 5 close friends, each with their own graph, so the Oct 22 launch has real users behind it; a fixed 30-question eval decides whether retrieval is good enough to show. The public brain and its public/private split stay in v4.

## Decisions

- **Agent-Reach is a reference, not a dependency.** [Agent-Reach](https://github.com/Panniantong/Agent-Reach) (MIT) is a router for interactive coding agents. It installs and health-checks other people's tools, and it switches between them automatically when a platform breaks one ("Bilibili 412-blocked yt-dlp → switched to bili-cli, zero action on your side"). That conflicts with our pinning rule, and its tools are built to search and browse, while we need to fetch the one item behind a URL. We use its research to pick one pinned tool per source (below). The owner can still install it as a Claude Code skill; that's independent of this project.
- **"Search anything" means ingesting any link sent to the bot.** The bot doesn't search the web. Claude Code and Codex already do that themselves; this project's job is to remember.
- **The MCP connector is read + write.** Mid-conversation, Claude can save something to the graph ("remember this link"), not just query it.

Two notes that outlive v3:

## Link filtering

**Decision: a link to something with nothing to remember gets a "not supported" reply and is never saved.** Two checks, matching the existing two-layer URL validation:

1. **Before fetching (Worker 1, by URL shape).** Profiles, feeds, listings, search pages, and anything else that's navigation rather than content are rejected with the existing "Skipped (not ingestible): <url> — <reason>" reply. No job is created.
2. **After fetching (Cloud Run, by content).** If the page turns out to have no useful content, it isn't summarized or written to the graph. The bot replies "not supported: <reason>" and the job ends `failed` with that reason. See [No useful content](#no-useful-content).

Playwright stays as the blog renderer. Only the "save whatever came back" behavior goes.

For the first check, the rules live in one table in `workers/ingest/src/urls.ts` (host + path pattern + reason), so adding a rule later is one line. This is the same Layer-1 check that already rejects Instagram profiles and YouTube channels; it now covers the new sources and adds a set of general rules for any host.

Today any unrecognized link is treated as a blog, so an X profile or a Google search page currently goes into the blog pipeline, gets rendered, and saves whatever the page shows (often a login wall).

| Reddit (`reddit.com`, `www.` / `old.` / `new.` / `np.` / `m.`, `redd.it`) | `/r/{sub}/comments/{id}/…` (post), `/r/{sub}/comments/{id}/{slug}/{comment_id}` (that comment), `/comments/{id}`, `redd.it/{id}`, `/r/{sub}/s/{token}` share links (resolved when fetched) | **Post only, no comments.** A comment link saves that comment, with the post's title for context |

**Until each source's fetcher is built,** links Worker 1 now labels `x`, `reddit`, `stackexchange`, `github`, or `pdf` go to the orchestrator's placeholder, the same way YouTube and Instagram links do today: they sit at 👀. Before, they went through the blog pipeline and saved whatever the page rendered.

**The private-network rule is a security fix, not tidiness.** Cloud Run can reach private IPs through Direct VPC egress, including FalkorDB (`10.128.0.2`) and its browser UI (port 3000). Once links inside fetched posts become their own jobs (v4, see [Moved to v4](#moved-to-v4)), link targets can come from a stranger's post, not just the owner. Layer 1 catches literal addresses, including disguised forms (`http://2130706433/` parses to `127.0.0.1`). At fetch time (`fetcher.render`, built 2026-09-26), Cloud Run resolves every request the browser routes (the first navigation and every subresource) and aborts any that points at a non-public address. Redirect hops bypass Playwright's routing (verified: neither `page.route` nor fulfilling the 3xx sees the next hop), so every request is also recorded, and if any reached a non-public address the page is discarded before extraction. A redirect can still cause one blind GET, but nothing it returns is kept, and the internal targets are safe from a bare GET: Redis drops HTTP, and the GCP metadata server requires a header browsers can't send. Live check: a public page redirecting to `127.0.0.1`, a public hostname resolving to it (`localtest.me`), and a literal address all got "not supported"; ordinary articles and public-to-public redirects still saved. Resolve-then-connect leaves a DNS-rebinding window between the check and Chromium's own lookup; the recorded-requests check narrows it but doesn't close it.

### No useful content

What counts as "no useful content", measured on real pages (plain download + Trafilatura, 2026-09-26):

| Page | Extracted text |
|---|---|
| The 8 M0 blog posts, Substack, Hugging Face, react.dev | 6K–67K chars |
| Hacker News front page | 4K chars |
| GitHub home page | 2K chars |
| Medium, OpenAI, NYT | Blocked by bot protection (403): 41–460 chars of error page |

- **HTTP error** (4xx/5xx after redirects): "not supported: the site returned HTTP <status>".
- **Too little text**: under `MIN_ARTICLE_CHARS` = 1,000 extracted chars (tune on real traffic), "not supported: no article text found". That catches login walls, bot-challenge pages that answer 200, and empty shells. It doesn't catch busy listing pages; those are what the URL rules are for.

Built 2026-09-26 (`fetcher.PageBlocked`, `main.MIN_ARTICLE_CHARS`). Checked with the real Playwright renderer:

| Page | Outcome |
|---|---|
| Lilian Weng, Anthropic, Paul Graham | Saved (38K, 13K, 67K chars) |
| Medium, NYT | Not supported: HTTP 403. Playwright doesn't get past their bot protection either |
| OpenAI | Not supported: no article text (a 200 challenge page, 100 chars) |
| example.com | Not supported: no article text (112 chars) |
| A 404 | Not supported: HTTP 404 |
| Hacker News front page | Saved (4.5K chars), so it got a URL rule: listings rejected, `item?id=` pages kept |
- **Page metadata can't be the test.** Only 6 of the 10 real articles above declare themselves as an article in structured data; Anthropic, Simon Willison, and Paul Graham don't.

**Later:** short links (`bit.ly`, `t.co`, `tinyurl.com`) are accepted and resolved when fetched, so the URL rules never see their real destination. Resolving them in Worker 1 first is parked in ROADMAP future ideas; the fetch-time checks still apply.

## MCP connector

**Status: spec (2026-09-29), not yet built.** Lets Claude (claude.ai, Desktop, mobile, Claude Code) and Codex search the graph and save to it mid-conversation. Owner-only: every reader is the owner, so search sees the whole graph (the public/private split is v4). *(Changed 2026-10-08: each [friend](#friends-decided-2026-10-08) signs in to their own graph.)*

### Shape

```text
claude.ai / Desktop / Claude Code / Codex
        │  Streamable HTTP, Authorization: Bearer <token>
        ▼
kb-mcp  (new Cloudflare Worker, stateless)
  ├─ OAuth 2.1: /authorize → Google sign-in (owner only) · /token · /register · /.well-known/*
  └─ /mcp  tools/list · tools/call   (rate-limited — see Limits)
       ├─ search_memory  ──X-KB-Secret──▶ kb-orchestrator POST /search ──VPC──▶ FalkorDB
       └─ save_to_memory ──service binding (RPC)──▶ Worker 1 createJobs()
                                  → bot posts "Saving from <client>: …" in Telegram
                                  → D1 rows → queue → the normal pipeline → 👌
```

**Why a Worker, not Cloud Run.** Claude gives OAuth discovery, registration, and token endpoints 10 seconds to respond ([Claude connector auth docs](https://claude.com/docs/connectors/building/authentication)); a Cloud Run cold start (Graphiti + the Playwright image) can exceed that, and a missed refresh means intermittent disconnects. A Worker is always warm. [`@cloudflare/workers-oauth-provider`](https://github.com/cloudflare/workers-oauth-provider) implements the OAuth side (DCR, CIMD, PKCE S256, refresh-token rotation, RFC 8707 resource-bound tokens), with tokens in Workers KV. MCP 2026-07-28 made the protocol stateless (no `initialize` handshake, no session id), so the handler needs no Durable Objects. Graph reads still go to Cloud Run, because FalkorDB is VPC-private.

**Libraries (built 2026-09-29):** `@cloudflare/workers-oauth-provider` 1.2.1 (one `OAuthProvider`: authorization server and its only resource) and `@modelcontextprotocol/server` 2.2.0, the SDK's stable v2 line for the 2026-07-28 spec, whose `createMcpHandler` also serves 2025-era clients through a stateless fallback. Not Cloudflare's `agents` package: it wraps the same SDK and pulls in esbuild, Rolldown, and React peers for features this server doesn't use.

**Consent page.** Every client sees a consent page before Google, showing its name (marked unverified for a self-registered client), where access will be sent, and a warning when that's an app on this computer. This is required, not decoration: without it, anyone could register a client, send the owner a link, and, since Google skips its own prompt once consented, receive a token. The library's consent and upstream helpers bind the page and the Google `state` to the browser with single-use cookies; `src/auth.ts` renders the page and runs the Google leg with PKCE.

### Tools

Two tools, aimed at the tasks rather than wrapping Graphiti's API. No delete or clear tools: a model must never be able to erase memory.

**`search_memory`** — read-only (`readOnlyHint: true`).
- Input: `query` (string, required), `limit` (integer, default 10, max 30).
- Runs Graphiti's hybrid search (semantic + BM25, RRF-ranked) over facts (`RELATES_TO` edges).
- Each result: the fact sentence, when it became true (`valid_at`) and, if superseded, when it stopped (`invalid_at`), and its source: the episode's title and URL (from `source_description`), or "Telegram note" with its date.
- Returns readable text: a numbered list of facts, each with its source line. Never returns episode bodies (full article text): too many tokens, and facts plus a link are what a conversation needs.
- No results → says so, not an error.

**`save_to_memory`** — write (`readOnlyHint: false`, `destructiveHint: false`).
- Input: `content` (string, required, ≤ 4,000 chars, so the "Saving from" echo fits Telegram's 4,096-char message cap): a link, several links, or a note. Processed exactly like a Telegram message: links fan out into URL jobs through the same Layer-1 rules; text with no links becomes a note.
- Returns right away: the jobs created (id + URL or "note") and any links rejected with their reason (e.g. "X profile/page, not a post"), so the model can tell the user immediately. Processing is asynchronous; the 👌 in Telegram marks it done.
- Description tells the model to save only when the user asks, because sending is the curation act.

### Save path

`kb-mcp` calls a new RPC method on Worker 1 through a service binding (a `WorkerEntrypoint`, callable only by bound Workers, not from the internet, so it needs no shared secret):

1. Worker 1 sends "📥 Saving from <client name>: <content>" to `OWNER_CHAT_ID`. The client name comes from the OAuth registration (e.g. "Claude", "Codex").
2. It builds jobs with the existing `buildTextMessageJobs`, using that bot message's `chat_id` / `message_id` and `content` as the text. No schema change, and dedup on `(chat_id, message_id)` still holds.
3. Insert → enqueue → `queued`, then 👀 on the bot message, exactly as `handleUpdate` does. Rejected links are replied to in Telegram too.

To verify when building: that a bot can set a reaction on its own message (`setMessageReaction`); if not, the 👀/👌 go on nothing and the summary reply alone confirms.

### Sign-in: Google (decided 2026-09-29)

OAuth needs the owner to prove who they are once per client; after that the Worker's own refresh tokens keep the client connected. The Worker sends the owner to Google, then issues its own token only if Google returns the owner's account id (a Worker secret). The OAuth client lives in the existing GCP project (free). Its consent screen stays in Testing mode with only the owner as a test user, so Google itself refuses anyone else. Google's 7-day refresh-token limit in Testing mode doesn't matter: Google is used only at sign-in, never afterwards. Scopes: `openid email` only, so no Google verification review.

Redirect URIs to accept: `https://claude.ai/api/mcp/auth_callback` (hosted Claude apps), and loopback `http://localhost/…` / `http://127.0.0.1/…` on any port (Claude Code, Codex). The library matches loopback redirects port-agnostically (RFC 8252), checked in `workers/mcp/test/oauth.test.ts`. Refresh tokens rotate on use; a grant lives while its client refreshes at least every 30 days (`refreshTokenIdleTTL`).

### Limits (decided 2026-09-29)

Goal: stay inside Cloudflare's free tier and the downstream free quotas. Cloudflare doesn't meter Workers bandwidth (ingress or egress) on any plan; the free plan meters requests: **100,000 Worker requests/day, shared by all Workers on the account** (reset 00:00 UTC), and **KV at 1,000 writes/day**. Exceeding them doesn't bill, it fails (Error 1027), which would also take down the Telegram webhook. So the caps protect availability first, and the metered downstreams (OpenAI credit, Supadata's 100 videos/month, Gemini) second.

| Cap | Value | Protects |
|---|---|---|
| Burst, both tools together | 30 calls / UTC minute | a looping agent |
| `search_memory`, daily | 500 / UTC day | Cloud Run + OpenAI embeddings |
| `save_to_memory`, daily | 50 / UTC day *(replaced 2026-10-08 by [per-user caps](#friends-decided-2026-10-08) that count Telegram and connector saves together)* | OpenAI extraction (gpt-4.1-mini complimentary tokens), Gemini, Supadata |

- **All counted in D1, only for signed-in tool calls** (`workers/mcp/src/limits.ts`, table `usage` from migration `0004`). Each call is one D1 batch: delete expired windows, then upsert-and-return the minute and day counters. Not KV: its 1,000 writes/day go to OAuth tokens. Not the Workers Rate Limiting binding: its counters are approximate and per location, and D1 already has to be written for the daily caps. At the caps, that's about 1,100 rows written a day, against D1's 100,000.
- **Over a cap:** the tool call returns a tool error (`isError: true`) saying which cap and when it resets, so the model can tell the user. Calls over a cap still count, so a looping client stays blocked for the rest of the window.
- **Dropped from the first draft: a daily cap on all `kb-mcp` requests.** It couldn't protect the shared 100k: Cloudflare counts a request when it reaches the Worker, so rejecting it saves nothing. And counting every request, signed in or not, in D1 would let junk traffic spend the D1 writes the job pipeline needs. The remaining exposure: someone hammering the public URL can use up the day's 100k Worker requests, which makes the Telegram webhook fail until 00:00 UTC (Telegram retries its deliveries) but can never cause a charge. The free plan has no WAF on `workers.dev`.

### Search endpoint

`POST /search` on `kb-orchestrator`, behind `X-KB-Secret` like `/jobs`. Body `{query, limit}`; returns the result list above. It reuses the lazily built Graphiti client from `graph.py`. One embedding call per query (`text-embedding-3-small`); no LLM call, since Graphiti's default search reranks with RRF, not a model. A cold start adds a few seconds to the first search, acceptable for a tool call (the 10-second limit applies only to the OAuth endpoints). Built 2026-09-29 (`graph.search_facts`).

Found while building it, checked on the live graph (9 episodes, 108 facts):

- **BM25 never matched anything.** Graphiti filters its FalkorDB fulltext query on the group, escaped as `"second\-brain"`, but the fulltext tokenizer splits the stored value at the hyphen, so the filter matches nothing and every keyword search returns empty. Search passes no `group_ids` (the driver's graph already is the group), and keyword results came back. **Ingestion has the same bug:** `add_episode` finds duplicate and contradicting facts with the same group-filtered hybrid search (`graphiti_core/utils/maintenance/edge_operations.py`), so since v2 only its embedding half has worked; entity dedup is embedding-only and unaffected. Fix: graph names that are one fulltext token (letters and digits only), which needs a rebuild. The v4 partition rebuild creates new graphs anyway, so name them that way.
- **No similarity cutoff works.** FalkorDB reports similarity as `(1 + cosine) / 2`, so Graphiti's default floor of 0.6 means cosine > 0.2 and lets nearly everything through. Raising it doesn't help: relevant facts scored 0.35–0.46 cosine and unrelated ones 0.25–0.41. The search returns the top results unfiltered, and the calling model judges relevance. A cross-encoder rerank (`gpt-4.1-nano` via Graphiti's `OpenAIRerankerClient`) separated relevant from unrelated sharply (~0.98 vs ~0.0) but was too strict ("what did Karpathy say about 2025" scored 0 on facts from his post, which don't name him); not adopted.
- **Extraction is thin on long articles.** No fact in the graph contains "memory", though the Lilian Weng agents article (38K chars) has a whole section on agent memory; the 9 episodes average 12 facts each. Search can't find what extraction never wrote. Not an MCP problem; see [open question 7](#open-questions).

## Long content: section episodes (decided 2026-09-30)

**Problem** (open question 7): a 38K-char article yields about a dozen facts, and whole sections go unextracted. Graphiti 0.30.2 doesn't chunk text. Its `utils/content_chunking.py` is never called, and its rules exempt prose ("news articles, documentation") anyway. So the whole article goes into a single entity-extraction call of about 9.5K tokens. That prompt is tuned to leave things out ("When in doubt, do NOT extract"), and facts are only extracted between entities it found, so a missed entity costs its facts too. There's no second pass for missed entities (Microsoft GraphRAG's "gleaning") either.

**Evidence.** Microsoft's GraphRAG paper ([2404.16130](https://arxiv.org/abs/2404.16130), Appendix A.2) found GPT-4 extracted almost twice as many entity references from 600-token chunks as from 2,400-token ones. Its experiments split the corpus into 600-token chunks with 100-token overlaps. Recent GraphRAG papers (Mar–Aug 2026) all extract from bounded units or add a recovery step. The two most relevant:
- [HVM-GraphRAG](https://arxiv.org/abs/2607.24861): giving each chunk its place in the document was its biggest ablation gain.
- [MemGraphRAG](https://arxiv.org/abs/2606.00610): keeping extraction consistent across chunks needs shared context.

**Decision:**
- **Split like the Microsoft paper.** Every episode body over 600 tokens is cut into fixed 600-token sections with a 100-token overlap, on token boundaries. The token counts come from tiktoken `o200k_base`, `gpt-4.1-mini`'s tokenizer, pinned. Its encoding file is baked into the image so cold starts don't download it. This applies to every content type, since it's one rule on the episode body. Short items (most notes, X posts) stay a single section.
- **Each section is its own Graphiti episode, written in index order,** with the job's title as its name. Section `i` has index `i`, from 0. The Episodic uuid is `job_id` for section 0, so existing single-episode items keep their uuid, and `uuid5(job_id, str(i))` for the rest. Uuids stay deterministic, so re-running a job upserts the same episodes instead of duplicating them. `source_description` gets a trailing ` | section: i/n`. `parse_source` only reads the part before the first ` | `, so it's unaffected.
- **Keep the last 3 sections, by index, not timestamps.** Each `add_episode` call passes `previous_episode_uuids` = the uuids of sections `i-3 … i-1` of the same job. This is Graphiti's own window size (`EPISODE_WINDOW_LEN = 3`). Section 0 passes `[]`. Without it, Graphiti falls back to the 3 most recently created episodes in the whole graph, which are unrelated items. The reference time stays `time_received` for every section. Order comes from the index alone, so sections sharing a timestamp or another job's episode landing in between can't scramble the context. This changes context for every item, notes included: a note no longer sees whatever was saved just before it.
- **The job state machine is unchanged.** One job, one `indexing` state across all its sections, then `saved`. If a section fails, the job fails. A retry re-runs every section, which is idempotent via the deterministic uuids.
- **Search deduplicates sources.** A fact can now come from several sections of the same item, so `search_facts` collapses sources with the same title, kind, and URL.

**Budgets to measure before rollout.** Both scale with the number of sections: about 19 for the 38K-char article, and about 40 for the longest X Article seen (80K chars).
- **Time:** sections run in sequence (one queue consumer, to keep Graphiti's entity dedup serial). Cloud Run's `--timeout 600` covered one call; if it doesn't fit, raise it toward the queue consumer's 15-minute wall-clock limit. Content still too long for that is v5's long-content work.
- **Tokens:** each section's prompts also carry up to 3 previous sections (~1,800 tokens), so a long article costs several times its old token count. That's measured against `gpt-4.1-mini`'s 2.5M complimentary tokens/day; overage draws on the $5 credit.

**Check:** re-extract the 38K-char article from open question 7 both ways, and compare:
- facts per 1K chars
- sections with zero facts
- tokens used
- wall time

Items already in the graph stay single-episode until they're re-driven from D1. That can happen together with v4's graph rebuild for the public/private split.

## YouTube home worker (decided 2026-10-08)

**Problem.** YouTube blocks Cloud Run's IPs: 3/3 `RequestBlocked` on 2026-09-26 and again on 2026-10-08 ([spike](../../spikes/youtube-transcript/)). Supadata works, but its free plan is 100 videos/month and it's a third party. From a home IP, youtube-transcript-api returns full captions in about 1s.

**Decision: a small worker on a home machine fetches captions; Supadata is the fallback.**

```
orchestrator (Cloud Run) ──HTTPS + secret──▶ Tailscale Funnel URL ──▶ worker on the home machine ──▶ YouTube
        └── worker unreachable or blocked ──▶ Supadata (as today)
```

- **The worker.** A Python service, `services/yt-worker/`, with one endpoint: `POST /transcript` with `{"video_id": ...}`. It returns the caption text, or a "no captions" error. It uses `youtube-transcript-api`, pinned (`1.2.4`, the spike's version), and listens on `127.0.0.1` only, so only the tunnel reaches it. It checks the `X-KB-Secret` header like every internal endpoint, but with its own secret (`YT_WORKER_SECRET`), not Worker 2's. The home machine is the least protected box in the system, so a leak there shouldn't open anything else.
- **The tunnel: Tailscale Funnel**, free on the personal plan, gives a stable public `https://<machine>.<tailnet>.ts.net` URL with no port forwarding. Not Cloudflare Tunnel: a stable hostname there needs our own domain on Cloudflare (a yearly fee), and its free quick tunnels get a new random URL on every restart.
- **Still request-triggered.** The orchestrator calls the worker inside the job's request, like any other fetcher. Nothing polls, and the state machine is unchanged (`fetching` covers the call).
- **Fallback rules** (in `sources._youtube_transcript`). *Superseded 2026-10-10 by [specs/youtube-home-worker.md](../../specs/youtube-home-worker.md): an unreachable worker or an unset `YT_WORKER_URL` no longer falls back to Supadata — the job is retried later, or fails as a setup mistake.*
  - Worker returns captions → use them. No Supadata credit spent.
  - Worker says the video has no captions → the existing `NO_CAPTIONS` reply, no Supadata call: Supadata's `native` mode would find none either.
  - Worker unreachable, times out (30s), errors, or reports `RequestBlocked` / `IpBlocked` → Supadata, as today.
  - `YT_WORKER_URL` unset → Supadata only. Nothing changes until the worker is set up.
- **Where it runs.** The owner's Mac first, then an old laptop running Linux once its charger arrives. The script, its venv, and the Funnel are the same on both. Only the service manager differs:
  - **Mac:** a `launchd` agent (`~/Library/LaunchAgents/`) with `RunAtLoad` and `KeepAlive`; no sleep while on power (`pmset -c sleep 0`).
  - **Linux:** a `systemd` unit with `Restart=always`, enabled at boot; the laptop ignores its lid (`HandleLidSwitch=ignore` in `logind.conf`).
  - Moving machines: copy the folder, rebuild the venv, start the Funnel, swap the service file, and point `YT_WORKER_URL` at the new machine (or give it the old machine's Tailscale name). The fallback covers the gap.
- **Cost.** $0/month in services: Tailscale's free plan, and no new GCP resources. One-time: the laptop's charger. Electricity for a laptop left on is a few dollars a year.
- **Risk.** Heavy use could get the home IP throttled too. At one person's volume that's unlikely, and the fallback still works.

**Check:** with the worker up, a captioned video goes end to end, and the orchestrator logs show no Supadata call. With the worker stopped, the same video goes through Supadata. A video with no captions gets the "no captions" reply without a Supadata call.

**Videos with no captions (decided 2026-10-08):** the worker gets a second endpoint that downloads the audio with yt-dlp (YouTube blocks that from Cloud Run too) for the [transcription](#transcription-decided-2026-10-08) step. So the "no captions" reply above only remains for when the worker is down.

## Friends (decided 2026-10-08)

**Decision: up to 5 close friends use the system alongside the owner, each with their own graph.** This reverses the 2026-09-26 "owner only" rule for this small, hand-picked group; it is not open sign-up. Accepted with it:
- **Data sharing.** Graphiti runs on OpenAI's data-sharing complimentary tokens, so friends' saves are shared with OpenAI like the owner's. Accepted by the owner for this group.
- **A small token bill.** Friends' extraction can run past the complimentary tokens into the prepaid OpenAI credit. Minimize it (below); auto-recharge stays off, so the most it can ever cost is what's been prepaid.

**Who's a user: a `users` table in D1** (a new migration in `workers/ingest`, the schema's single source of truth): `chat_id` (primary key), `name`, `google_email`, `graph`, `daily_saves`. It replaces both `OWNER_CHAT_ID` (Worker 1) and `OWNER_GOOGLE_SUB` (kb-mcp). The owner adds a friend with one `wrangler d1 execute` insert.
- **Telegram.** Worker 1 accepts a message only if its `chat_id` is in `users`; anyone else is still ignored silently.
- **Connector.** Google sign-in maps the verified email to a `users` row; no row, no token. Each friend is also added as a test user on the Google OAuth consent screen, which stays in Testing mode (up to 100 test users, no verification review). `save_to_memory` posts its "Saving from…" message to that user's own chat; `search_memory` searches only that user's graph.

**One graph per user.** The orchestrator picks the Graphiti graph from the job's `chat_id` (and `/search` from the signed-in user), instead of the fixed `second-brain`. Graph names are letters and digits only (`kb` + `chat_id`), which also fixes the [BM25 bug](#search-endpoint) for ingestion. The owner's `second-brain` is rebuilt into `kb<owner chat_id>` from D1, which also re-drives its items as section episodes. Separate graphs, not one graph filtered by user: Graphiti merges an entity across every episode that mentions it, so a filter at read time could leak one user's details into another's facts.

## Moved to v4

Moved 2026-09-29 so the MCP connector gets finished first. Kept here so the v4 design can pick them up. The public/private split moved with the public brain: it exists so private notes can't reach the public page, and until that page exists every reader of the graph is the owner.

**Link fan-out.** Links inside a fetched post become their own jobs. A post like "Nice @nytimes article… <url>" is saved as-is, and each URL in it is processed separately, as if it had been sent on its own. This applies to X, and the same rule fits Reddit link posts. Proposed mechanics, to confirm when building:
- **Only Worker 1 creates jobs.** Cloud Run finds links only after fetching, so it asks Worker 1 to create the children through an internal endpoint behind `X-KB-Secret`. That reuses Worker 1's Layer-1 URL checks and writes each D1 row before enqueueing, so every job stays rebuildable from D1. The MCP save path (v3) may build this endpoint first.
- **Children carry the parent's `chat_id` / `message_id`,** so `allJobsSaved` holds the 👌 until they're done too. D1 already allows several rows per message (multi-URL fan-out). Children must be created before the parent reaches `saved`, or 👌 fires early; creating them during `fetching` guarantees that.
- **One level deep.** A child's own links aren't fanned out again, which stops chains and loops. That needs a `parent_job_id` column (a new migration), which also records where the link came from.
- **Which links:** the post's expanded URLs (FxTwitter already resolves `t.co`). A quoted post's text goes into the parent's episode instead of becoming a child job.

**Partition** (resolve before any public retrieval code):
- **Two graphs or one?** Filtering one graph when it's read isn't safe: Graphiti merges an entity across every episode that mentions it, so a public entity's summary and facts can carry details from a private note. The candidate is two Graphiti graphs (on FalkorDB, `group_id` = graph name), with owner retrieval querying both. Cost: a private note no longer links to entities from public articles.
- **Which side does each content type default to** (blog/YouTube public; notes and voice private?), and how does a message override it? This extends the curation policy ("sending is the curation act") with a visibility decision. Includes which side an MCP save defaults to.
- **Rebuilding the existing graph.** `second-brain` holds both kinds of content, and MCP saves will add to it. Rebuild it into the split from D1 (every row carries enough to replay), then retire it.

**Public brain:**
- **What a public answer may contain.** Blog episodes hold the full article text, so episode content must never reach a visitor. Public answers come from facts, entities, and `source_description` links only.
- **Query cost and abuse.** What's the daily cap, enforced in the Worker before anything reaches Cloud Run? What do visitors see once it's hit? Are answers LLM-written, or just the returned facts (cheaper, and nothing for a prompt injection to steer)?
- **Where the page lives.** Candidate: a Cloudflare Worker/Pages front end → a Cloud Run query endpoint behind `X-KB-Secret`. FalkorDB stays VPC-private, and its browser UI (port 3000) stays tunnel-only.

**Weekly Leiden community recompute.** Design in [v2.md](v2.md#moved-to-v3). Improves retrieval but isn't needed for any v3 user journey.
